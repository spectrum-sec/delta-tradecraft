# Java4Shell pack

An out-of-bounds memory flaw in the OpenJDK HotSpot runtime on x86-64 hosts with AVX-512 (CVE-2026-114938), published 17 Nov 2026 ([CVE record](https://cveawg.mitre.org/api/cve/CVE-2026-114938)), which Azul also lists against Azul Prime ([Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)). The discoverer places it in the AVX-512 Base64 decode path used by `java.util.Base64` ([Calif](https://calif.io/java4shell)).

**3 objects, 16 detection strategies (5, 5 and 6 by object).** Built from public research with no atomic indicators and no request-level object: the pack publishes no request-matching criteria and uses GreyNoise's attempt counts only as status ([GreyNoise](https://java4shell.events.greynoise.io/)).

## Scope

CVE-2026-114938 only: the other fixes among the 11 Java SE flaws in Oracle's November update are out of scope ([Oracle](https://www.oracle.com/security-alerts/cspunov2026.html)). The runtime identity is read first from the VM name and a HotSpot build is affected when all of these hold, while Azul Prime takes the branch described after the list:

- HotSpot on an x86-64 JVM ([OpenJDK advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17)).
- Branch 17 from 17.0.6, 21, 25 or 27 built below the vendor's fix, the Oracle Java SE 8 Performance Pack below 8u513-perf with 8u511b33-perf as the affected build ([OpenJDK advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17), [Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018), [KISA](https://www.boho.or.kr/kr/bbs/view.do?bbsId=B0000133&pageIndex=1&nttId=72313&menuNo=205020), [CERT Polska](https://moje.cert.pl/komunikaty/2026/216/krytyczna-podatnosc-w-srodowisku-java-umozliwiajaca-zdalne-wykonanie-kodu-java4shell/)).
- The host CPU has avx512f, avx512bw, avx512vbmi and bmi2, as `/proc/cpuinfo` spells them or hypervisor and cloud inventory lists them ([Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018), [CERT Polska](https://moje.cert.pl/komunikaty/2026/216/krytyczna-podatnosc-w-srodowisku-java-umozliwiajaca-zdalne-wykonanie-kodu-java4shell/), [Sysdig](https://www.sysdig.com/blog/java4shell-cve-2026-114938-pre-auth-rce-in-openjdk)). HotSpot spells the third feature `avx512_vbmi` in the JVM's own CPU line and drops every AVX-512 token when effective `UseAVX` is below 3, so host flags present with a JVM line lacking AVX-512 are a `mitigated-not-patched` lead to confirm with the effective flag read below and never `not affected` ([OpenJDK source](https://github.com/openjdk/jdk/blob/master/src/hotspot/cpu/x86/vm_version_x86.cpp)). A verified host or guest-visible read that lacks one of the four features makes the JVM `not affected` (CPU-ineligible) and a missing CPU read stays `unknown` ([Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)).
- Effective `UseAVX` is 3 or more and `UseBASE64Intrinsics` is on, read with `jcmd <pid> VM.flags -all` on the live process ([Oracle jcmd](https://docs.oracle.com/en/java/javase/17/docs/specs/man/jcmd.html)). A launch script or `JAVA_TOOL_OPTIONS` is not proof ([SonarSource](https://community.sonarsource.com/t/security-advisory-java4shell-workaround-for-sonarqube/191330), [Keycloak](https://www.keycloak.org/2026/11/java4shell-vulnerability-cve-2026-114938)).

Azul Prime (VM name Zing or Prime) has its own JIT and is `affected` when three things hold with no flag read: an x86-64 JVM, a release below the fix of its own line and a host or guest CPU read showing AVX-512 (`avx512f`), since Azul says only "AVX-512 enabled" and names no feature list, which is this pack's reading ([Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)). Azul lists Prime on Java 8, 11, 17, 21 and 25 in both its body and its FAQ ([Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)) and its Prime CVE table adds 27 ([Azul Prime CVE fixes](https://docs.azul.com/prime/CVE-Fixes-November26)). Azul uses the same "AVX-512 enabled" phrase for its HotSpot builds, so a Prime JVM on a host with `avx512f` and no `avx512vbmi` may be over-reported. Stable 26.08 is fixed at 26.08.110.0 and Stable 26.02 at 26.02.510.0 and each release compares only with its own line, so a 26.08 release below 26.08.110.0 is not cleared by sitting above 26.02.510.0, and a Prime release on any other line or one that cannot be read stays `unknown` ([Azul Prime CVE fixes](https://docs.azul.com/prime/CVE-Fixes-November26)). The HotSpot flag conditions are recorded as inapplicable to Prime because no source says the flags mitigate it, so Prime is never `mitigated-not-patched` ([Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)).

Upstream OpenJDK Java 8 and 11 without `-perf` and ARM64 are not affected ([OpenJDK advisory](https://openjdk.org/groups/vulnerability/advisories/2026-11-17), [Adoptium](https://adoptium.net/news/2026/11/temurin-november-2026-cspu-java4shell)), which does not clear Azul Prime 8 and 11 ([Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)). Non-LTS lines 18 to 20, 22 to 24 and 26 stay `unknown`, and Amazon's "No Fix Planned" for them does not make them affected ([ALAS](https://explore.alas.aws.amazon.com/CVE-2026-114938.html)).

## Verdict words

Object 001 gives each JVM exactly one of four verdicts and objects 002 and 003 join on them.

- `affected`: every HotSpot condition above holds on the live process, or the three Azul Prime conditions hold.
- `mitigated-not-patched`: the build and CPU conditions hold and `UseAVX` is below 3 or `UseBASE64Intrinsics` is off on the live process, whoever set the flag, and Azul Prime never takes this verdict. It stays on the patch list and is re-read after every restart or container recreate, and CERT-EU and CCCS recommend the flags as a workaround ([CERT-EU](https://cert.europa.eu/publications/security-advisories/2026-021/), [CCCS](https://www.cyber.gc.ca/en/alerts-advisories/al26-029-critical-vulnerability-impacting-oracle-java-cve-2026-114938)).
- `not affected`: the live build is at or above the vendor fix, a verified host or guest-visible CPU read lacks a required feature (CPU-ineligible), or the runtime is out of scope (upstream Java 8 or 11 or ARM64), with the reason recorded inside the verdict ([Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018), [Azul](https://www.azul.com/blog/java4shell-cve-2026-114938-what-it-is-who-is-affected-and-what-to-do-now/)).
- `unknown`: a condition could not be read, a missing CPU read included, or the runtime is OpenJ9 or IBM Semeru with no vendor mapping, and the JVM is never reported as affected or cleared.

"Exposed" means network reachability only ([Red Hat](https://access.redhat.com/security/vulnerabilities/RHSB-2026-018)), which ranks the work and never clears a JVM.

Successful exploitation may leave no traces in logs, so a missing crash is no clearance ([CERT Polska](https://moje.cert.pl/komunikaty/2026/216/krytyczna-podatnosc-w-srodowisku-java-umozliwiajaca-zdalne-wykonanie-kodu-java4shell/)). Two analyst aids in these objects are this pack's own reasoning: a burst of requests before a crash ranks a crash candidate in 002 and never makes a finding ([VulnCheck](https://www.vulncheck.com/blog/java4shell)), and a crash loop followed by a shell child of the same service is joined on host and service from 002 to 003, a correlation CISA and Sysdig do not state because they name crashes and JVM-spawned shells only as separate signals ([CISA](https://www.cisa.gov/news-events/alerts/2026/11/17/critical-java-vulnerability-requires-immediate-patching), [Sysdig](https://www.sysdig.com/blog/java4shell-cve-2026-114938-pre-auth-rce-in-openjdk)).

## Telemetry checks

Telemetry was checked in a lab where the vulnerability was never triggered, with three results:

- **Flag output did not separate the sampled builds.** It was identical on 17.0.5, 17.0.6 and 17.0.21 so on those three builds the version string was the only separator, vendor version and packaging evidence decides for every other build (see Fixed builds) and Java 8 has no Base64 intrinsic flag ([OpenJDK flags](https://github.com/openjdk/jdk/blob/master/src/hotspot/share/runtime/globals.hpp)).
- **Not every fatal error is a SIGSEGV.** The fatal-error banner goes to stdout and the exit code was 134 under an init or shell parent. HotSpot opens the `-XX:ErrorFile` path first when one is set, then `hs_err_pid<pid>.log` in the working directory, then the temp directory, and takes the first that opens, so the default paths stay eligible when `ErrorFile` is set and the report is lost with an ephemeral container ([OpenJDK](https://raw.githubusercontent.com/openjdk/jdk17u/master/src/hotspot/share/utilities/vmError.cpp), [Oracle](https://docs.oracle.com/en/java/javase/17/troubleshoot/fatal-error-log.html)). The effective `ErrorFile` value is read from the live process where it can be collected because a captured command line may not show it, and a file record is labelled create, overwrite or generic write because a write hit alone does not prove a new report.
- **`jspawnhelper` runs first in the child's own process** on Linux JDK 17, so the target's parent is still `java` as recorded on native arm64 Linux ([OpenJDK](https://raw.githubusercontent.com/openjdk/jdk17u/master/src/java.base/unix/classes/java/lang/ProcessImpl.java)).

## Open gaps

- Windows crash behavior and process lineage were not lab-tested.
- The exit code of a JVM running as PID 1 was not measured.
- Real x86 AVX-512 flag values were not measured because x86 images ran under emulation, so the CPU and flag strategies in object 001 have no validation block.
